# 判断例（audit-test-quality）

**ここに出てくるファイル、関数、テスト、障害、仕様はすべて架空のもの**で、判断の考え方を示すためだけに使う。結論をそのまま他のテストに当てはめず、対象の根拠を確認する。

## 目次

1. 実装をなぞるテストを、独立した期待値に書き換える
2. 恒真の検証で、固有の役割もないため削除候補にする
3. `toBeDefined` が最低限の契約を検証している
4. 外部サービスへの呼び出し確認が有効な契約テストである
5. 重複ケースを統合しても、異なる境界値は維持する
6. 過去の障害を防ぐテストを、代替がないので維持する
7. ミューテーションを検出できなかったため、強化を提案する
8. 待機漏れの修正で本体のバグが現れた
9. 代替関係の循環を見つけた
10. 承認の解釈

## 1. 実装をなぞるテストを、独立した期待値に書き換える

```ts
// 架空：price.test.ts:12
test("税込価格を計算する", () => {
  const expected = Math.floor(999 * (1 + TAX_RATE));
  expect(priceWithTax(999)).toBe(expected);
});
```

**誤りやすい判断**：実装の繰り返しなので削除する。

**確認した内容**

- 【事実】実装も同じ式なので、式の誤りや `TAX_RATE` の誤りを検出できない。
- 【事実】`priceWithTax` が例外を投げる回帰や、呼び出し先の取り違えは検出できる。
- 【事実】仕様書に「税率10%、1円未満切り捨て」とある。

**判断**：書き換え。仕様という実装とは独立した出典から期待値を決める。

```ts
test("税率10%で1円未満を切り捨てる", () => {
  expect(priceWithTax(999)).toBe(1098); // 999 × 1.10 = 1098.9
});
```

**書き換えで検出できるようになる回帰**：丸め方向の誤り、税率定数の誤り。

## 2. 恒真の検証で、固有の役割もないため削除候補にする

```ts
// 架空：flags.test.ts:5
test("フラグが読み込める", () => {
  expect(FLAGS).toBe(FLAGS);
});
```

**確認した内容**

- 【事実】`FLAGS` がどの値でも同じ参照との比較なので、このアサーションは失敗しない。
- 【事実】テスト本体で本体の関数を呼んでいない。失敗の経路はモジュールの読み込みエラーだけ。
- 【事実】`flags_usage.test.ts:8` が同じモジュールを読み込み、`FLAGS.newCheckout` の既定値を検証している。CI対象でskipなし。
- 【推論】読み込みエラーの検出は `flags_usage.test.ts` で代替できる。

**判断**：削除候補。

| 必須項目 | 内容 |
| --- | --- |
| 検証する仕様 | 明確な仕様はない |
| 現在検出できる回帰 | モジュールの読み込みエラーのみ |
| 失われる検出能力 | なし（読み込みエラーは代替で検出） |
| 代替 | `flags_usage.test.ts:8` |
| 書き換えが適切でない理由 | 既定値の検証は代替に既にあり、書き換えても同じ内容になる |

実施は承認の後。

**判断が変わる条件**：次のようにアサーションの前で本体を呼んでいれば、恒真でも例外の検出というスモークテストの役割がある。同じ入力で呼ぶテストが他にないなら、維持か書き換えにする。

```ts
const report = buildReport(input);
expect(report).toBe(report);
```

## 3. `toBeDefined` が最低限の契約を検証している

```ts
// 架空：api/response.test.ts:20
expect(res.body.requestId).toBeDefined();
```

**誤りやすい判断**：弱いアサーションなので無意味。削除する。

**確認した内容**

- 【事実】API仕様で `requestId` は必須とされ、問い合わせ調査に使う。値の形式の規定はない。
- 【事実】このフィールドが欠ける回帰を検出できる。他のテストはこのフィールドを検証していない。
- 【事実】`null` や空文字になる回帰は検出できない。

**判断**：維持。弱さは記録する。空文字を不正とする仕様があると確認できれば、書き換え（強化）を提案する。仕様がないのに形式を推測して厳しくしない。

## 4. 外部サービスへの呼び出し確認が有効な契約テストである

```ts
// 架空：receipt.test.ts:33
await sendReceipt(order);
expect(mailer.send).toHaveBeenCalledWith({
  to: "buyer@example.test",
  template: "receipt",
  orderId: "A-1",
});
```

**誤りやすい判断**：モックの確認は実装をなぞっているので削除する。

**確認した内容**

- 【事実】`mailer.send` はメール配信サービスとの境界で、テストで実際に送信はできない。
- 【事実】宛先、テンプレート、注文IDは配信の契約で、誤ると顧客に影響する。
- 【推論】送信漏れ、宛先の誤りを検出する有効な契約テストである。

**判断**：維持。

**対比**：次は自分で設定した値を確認しているだけで、本体の振る舞いを検証していない。ただし、すぐ削除とせず、本体の処理を通す形に書き換えられないかを先に検討する。

```ts
repo.find.mockResolvedValue(order);
expect(await repo.find("A-1")).toBe(order); // 本体を通っていない
```

## 5. 重複ケースを統合しても、異なる境界値は維持する

架空の仕様：利用可能年齢は18歳以上。不正な値はエラー。

```ts
test("25歳は可", () => expect(canUse(25)).toBe(true));
test("40歳は可", () => expect(canUse(40)).toBe(true));
test("18歳は可", () => expect(canUse(18)).toBe(true));
test("17歳は不可", () => expect(canUse(17)).toBe(false));
test("負の値はエラー", () => expect(() => canUse(-1)).toThrow());
```

**確認した内容**

- 【事実】仕様の境界は18だけで、25と40は同じ区分。
- 【事実】18と17は境界の両側で、`>=` を `>` に変える回帰などを検出する。
- 【事実】-1は異常系で、別の経路を通る。

**判断**：統合。全ケースをパラメータ化し、境界値と異常系を残す。

```ts
test.each([
  [18, true],
  [17, false],
  [25, true],
  [40, true],
])("年齢 %i の利用可否は %s", (age, expected) => {
  expect(canUse(age)).toBe(expected);
});

test("負の値はエラー", () => expect(() => canUse(-1)).toThrow());
```

25と40のどちらかを減らすかどうかは、効果が小さいので今回は変更しない。

## 6. 過去の障害を防ぐテストを、代替がないので維持する

```ts
// 架空：coupon.test.ts:71
test("カートが空でクーポンありでも例外を投げない", () => {
  expect(applyCoupon(emptyCart, coupon).total).toBe(0);
});
```

**誤りやすい判断**：`checkout.integration.test.ts` が同じ `applyCoupon` の行を通っており、カバレッジも変わらないので削除する。

**確認した内容**

- 【事実】コミット履歴が、空カートのゼロ除算による障害記録を参照している。
- 【事実】結合テストは商品ありのカートだけを使い、空カートを通らない。
- 【事実】このテストを除いても行カバレッジは変わらない。
- 【推論】同じ行を通っても、ゼロ除算の回帰は結合テストでは検出できない。

**判断**：維持。カバレッジが同じことは、同じ不具合を検出できることを意味しない。

## 7. ミューテーションを検出できなかったため、強化を提案する

```ts
// 架空：shipping.test.ts:9
test("高額注文は送料無料", () => {
  expect(shippingFee(20000)).toBe(0);
});
```

仕様：10000円以上は送料無料、10000円未満は送料500円。

**検証**：リポジトリの外に作った一時コピーの `shipping.ts` で、`total >= 10000` を `total > 10000` に変えた。変異なしのテスト成功を確認した後で実行し、テストは通った（未検出）。対象リポジトリに差分が増えていないことを確認した。

**誤りやすい判断**：変異を検出できないので、このテストは不要。削除する。

**解釈**

- 【事実】20000円では、この変異で結果が変わらない。
- 【推論】変異は仕様に関係があり、振る舞いが変わる。原因はテストが境界を通らないこと。
- 【事実】このテストは、送料無料の処理が丸ごと壊れる回帰は検出できる。

**判断**：書き換え（強化）。

```ts
test.each([
  [20000, 0],
  [10000, 0],
  [9999, 500],
])("注文額 %i の送料は %i", (total, fee) => {
  expect(shippingFee(total)).toBe(fee);
});
```

変更後に同じ変異を同じ手順で実行して比較する。検出できても、回帰検出能力が完全に保証されたとは書かない。

## 8. 待機漏れの修正で本体のバグが現れた

```ts
// 架空：export.test.ts:18（承認された T-04 の書き換え対象）
test("出力に失敗したらエラーになる", () => {
  expect(exportCsv(badInput)).rejects.toThrow(); // await がない
});
```

`await` を追加すると失敗した。`exportCsv` は失敗時に例外を投げず、空ファイルを出力している。

**やってはいけないこと**

- 本体を直す。
- 期待値を「空ファイルになる」に変えて通す。
- skipして完了扱いにする。

**対応**：T-04を止めて報告する。報告には、仕様の該当箇所、再現手順、実際の結果を含める。本体の修正は別作業とし、T-04の扱いは利用者が決める。仕様が不明なら要確認とする。

## 9. 代替関係の循環を見つけた

候補ごとに見ると、次の判断は両方もっともらしい。

- T-07 `toolbar_save.test.ts`：`menu_save.test.ts` と同じなので削除候補
- T-08 `menu_save.test.ts`：`toolbar_save.test.ts` と同じなので削除候補

**残存テスト集合で確認**：両方を消すと、保存処理を検証するテストが残らない。

**判断**：どちらか1つを残すか、1つに統合する。入口ごとの差（無効状態の判定など）があるなら、その差のケースも残す。

## 10. 承認の解釈

| 利用者の返答 | 解釈 |
| --- | --- |
| 「いいね」 | 承認ではない。実施するIDと処理を尋ねる |
| 「続けて」 | 承認ではない。実施するIDと処理を尋ねる |
| 「T-02を書き換え、T-05とT-06を統合」 | この3件だけを実施する。残存テスト集合を確認し直す |
| 「全部お願い」 | IDと処理の一覧を示して確認してから進む |
| 「T-07を削除」（T-08の代替としてT-07を割り当てていた） | T-08の根拠が崩れるので、影響を説明して再承認を求める |
| 実装中に、テスト設定の変更が必要だと判明 | 止めて別途承認を求める |
