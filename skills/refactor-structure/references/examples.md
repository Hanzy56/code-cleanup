# 判断例（refactor-structure）

**ここに出てくるファイル、関数、テスト、障害、仕様はすべて架空のもの**で、判断の考え方を示すためだけに使う。結論をそのまま他のコードに当てはめず、対象の根拠を確認する。

## 目次

1. 見た目は重複しているが、共通化しない
2. retryが外部サービスの制約に必要なので維持する
3. 複数の特殊処理を、1つの設計改善で解消する
4. テストの意味を変える必要があり、別PRへ分割する
5. 同じ仕様の複製が食い違っている
6. 未使用に見えるコードにテストが付いている
7. 機械的な追従として認められる範囲
8. 承認の解釈

## 1. 見た目は重複しているが、共通化しない

**観測**：`billing/invoice_total.ts:24` と `reports/revenue_summary.ts:51` に、ほぼ同じ計算がある。

```ts
const total = Math.floor(lines.reduce((sum, l) => sum + l.amount, 0) * (1 + rate));
```

**誤りやすい判断**：重複なので `calcTotal()` に共通化する。

**確認した内容**

- 【事実】請求書側は請求仕様書の端数処理の規定を参照している。
- 【事実】集計側は経理チームの月次レポート定義を参照している。
- 【事実】過去2年の履歴で2箇所が同時に変更されたコミットはなく、集計側だけ丸め方の変更が1回あった。
- 【推論】現在の形が一致しているのは偶然で、別の理由で変更される。

**判断**：維持。共通化すると、請求の変更が集計へ、集計の変更が請求へ波及する。

**判断が変わる条件**：両者が同じ仕様を参照している、または片方だけの更新で不具合が出た履歴がある場合は、再検討する。

## 2. retryが外部サービスの制約に必要なので維持する

**観測**：`clients/shipping_api.py:88` に、HTTP 429のとき `Retry-After` の秒数だけ待って最大3回再試行する処理と、`sleep` がある。

**誤りやすい判断**：sleepとretryは設計の不備を隠す特殊処理なので削除する。

**確認した内容**

| 確認項目 | 結果 |
| --- | --- |
| 満たす要件・外部制約 | 【事実】配送APIの仕様に、429時は `Retry-After` に従うよう記載がある |
| 過去の障害 | 【事実】直前のコメントが、ピーク時の出荷失敗の障害記録を参照している |
| 今も必要か | 【推論】レート制限は現行仕様にもあり、必要 |
| 設計変更で不要にできるか | 【推論】キュー方式で隠せる可能性はあるが、振る舞いと運用が変わるため構造変更の範囲を超える |

**判断**：維持。コメントも保持する。キュー化は構造変更ではなく、別の提案として記録する。

**対比**：理由が同じように確認できても、同じretryが5箇所に複製されているなら、「retry方針の置き場所を1つにする」改善案は成り立つ。その場合も回数、待機、対象ステータスは維持する。

## 3. 複数の特殊処理を、1つの設計改善で解消する

**観測**

- `orders/list.ts:42`：`if (status === "legacy_paid") status = "paid"`
- `orders/invoice.ts:88`：同じ分岐
- `orders/refund.ts:17`：`status === "paid" || status === "legacy_paid"`
- `orders/export.ts:31`：DBの値をそのままCSVへ出力

**共通原因**：【事実】旧システムから移行した値がDBに残り、読み出し側の各所が個別に変換している。

**改善案**

```md
- R-01：`orders/repository.ts` の読み出し時に `legacy_paid` を `paid` へ正規化し、元の値は `rawStatus` に保持する
  - P-01：`orders/list.ts:42` の変換
  - P-02：`orders/invoice.ts:88` の変換
  - P-03：`orders/refund.ts:17` の二重比較
```

**変えてはいけない振る舞い**：CSV出力は引き続き `legacy_paid` を出力する。外部の連携先が読むため、【事実】連携仕様に記載がある。`export.ts` は `rawStatus` を出力するように変える。

**安全だと判断した根拠**

- 【事実】`legacy_paid` を読む箇所は上記4箇所で、文字列検索と型定義で確認した。
- 【事実】書き込み経路に変更はない。
- 【未確認】DBを直接読む外部の分析クエリは確認できない。ただし、DBの値は変えないので影響しない想定（【推論】）。

**検証**：既存テストを変更せずに前後で比較する。CSV出力の一致を確認する。

**注意**：`legacy_paid` への対応は消えたのではなく、1箇所へ移動した。特殊処理の数が減ることが目的ではなく、次にこの値を扱う変更が1箇所で済むことが効果。

## 4. テストの意味を変える必要があり、別PRへ分割する

**観測**：`cart/total.ts` の割引と税の計算を1つのパイプラインにまとめたい。`cart/total.test.ts:30` は次を検証している。

```ts
expect(applyDiscountSpy).toHaveBeenCalledBefore(applyTaxSpy);
```

**問題**：パイプライン化すると `applyDiscount` は内部関数になり、合計金額が同じでもこのテストは失敗する。

**誤りやすい判断**：
- スパイの検証を消して先に進む（検証の弱体化）
- 「機械的な追従」として書き換える（検証観点の変更なので当たらない）

**対応**：作業を止めて分割を提案する。

```md
- PR A（テストのみ）：「割引の後に税を計算する」という順序の仕様を、金額の期待値で検証するように書き換える。本体は変更しない。
- PR B（構造のみ）：PR Aのテストを変更せずに、パイプライン化する。
```

PR Aは本体を変えずに通ることで、書き換えたテストが現在の振る舞いを捉えていることを確認できる。PR Bはテストを変えずに通ることで、振る舞いの維持の根拠になる。

## 5. 同じ仕様の複製が食い違っている

**観測**：`signup/validate.ts:12` はパスワード8文字以上、`profile/change_password.ts:40` は10文字以上を要求している。同じパスワード規則に見える。

**誤りやすい判断**：共通関数に統一する。どちらかの振る舞いが変わるのに、構造変更として扱ってしまう。

**対応**：差を【事実】として記録し、どちらが正しいかは仕様の判断として利用者に確認する。統一は別の変更として提案する。振る舞いを変えない範囲の改善案（規則の定義場所を1つにして、2つの値をそのまま持つなど）は、効果があるときだけ提案する。

## 6. 未使用に見えるコードにテストが付いている

**観測**：`utils/legacy_format.ts` は本体から参照がない。`utils/legacy_format.test.ts` だけが参照している。

**確認**：パッケージの公開エントリ、動的import、設定ファイルからの参照を確認する。公開エントリに含まれていれば、外部利用者がいる可能性があり、未使用とは言えない。

**対応**：本体から未使用だと確認できても、削除にはテストの削除が伴うので、このSkillの中では実施しない。「未使用の可能性」として記録し、テストの扱いを含む別の変更として提案する。

## 7. 機械的な追従として認められる範囲

| 変更 | 判断 |
| --- | --- |
| ファイル移動に伴うimportパスの更新 | 認められる（計画に明記し承認が必要） |
| 関数名変更に伴う呼び出し箇所の更新 | 認められる（同上） |
| 同じ境界をモックしていて、パスだけ変わる | 認められる（同上） |
| 移動により別の層をモックすることになる | 認められない。検証範囲が変わる |
| テスト名の変更でsnapshotのキーが変わる | 認められない。snapshot更新は別途判断する |
| 期待値やアサーションの変更 | 認められない |
| 失敗したテストのskip | 認められない |

## 8. 承認の解釈

| 利用者の返答 | 解釈 |
| --- | --- |
| 「いいね」 | 承認ではない。実施するIDを尋ねる |
| 「続けて」 | 承認ではない。実施するIDを尋ねる |
| 「R-01を提案どおり実施」 | R-01だけを実施する |
| 「R-01を実施。ただし `export.ts` は触らないで」 | 計画を修正して示す。成り立たなければ理由を説明する |
| 「全部お願い」 | IDの一覧を示して確認してから進む |
| 実装中に、R-01で計画外のファイルの変更が必要だと判明 | 止めて再承認を求める |
